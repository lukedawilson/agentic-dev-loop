# Domain Entities - Unit 13 (Reporting Viz Extension)

View model for the historical runs view. Every entity descends from real data: unit-12 `reporting/sources.py` run records, `reporting/metrics.py` metric dicts, and the unit-9 viz asset conventions. No entity is invented for convenience.

## Entities

### RunsPage (the list view, served at /runs)
The HTML page listing runs with aggregate metrics and filter controls. Built by tools/build_viz_page.py from `viz/assets/runs.html` + `viz/assets/runs.js` + the shared `styles.css`, following the unit-9 pattern (marker inlined, generated file carries the "Generated by" header).

- **Descent**: unit-9 page.html/page.js conventions; live page gets a History link (FD-Q1 A).
- **Fields**: server URL (same origin), no config, reads /runs/data.

### RunDetailPage (the per-run view, served at /runs/<id>)
Same asset shell as the runs page; client-side detects the <id> from the pathname and fetches /runs/<id>/data. Unknown id renders the not-found state.

- **Descent**: FD-Q1 A (separate page), BR-7 (404 state).

### RunsListPayload (JSON, GET /runs/data)
Serialized list + aggregate for the current filters.

- **Descent**: `reporting.sources.build_run_records` + `reporting.metrics.pure_metrics` output shape.
- **Fields**: filters {since, until, statuses}, records [RunRecordSummary], metrics {loop_health, tdd, review, qa, threads} with each metric as MetricPayload, notice (degradation notes).

### RunRecordSummary
The per-thread row: thread_id, run_dir, subject, ts_start, ts_end, status, attempt_count, verdict_summary. Subset of unit-12 RunRecord, serialized explicitly (no raw dataclass dump).

- **Descent**: RunRecord fields (ts_start_dt, status, attempt_count(), attempt_verdicts()).

### RunDetailPayload (JSON, GET /runs/<id>/data)
Everything for the detail view: run_id, thread list with attempts and verdict sequences, per-thread metrics, artifact facts.

- **Descent**: RunRecord + ProseFacts + pure_metrics per-thread sections.
- **Fields**: run_id, threads [{thread_id, subject, ts_start, ts_end, status, attempts [{number, verdicts [{step, verdict, provenance}]}], metrics}], artifacts {brief, summary, findings, qa} (presence + key facts), notice.

### MetricPayload
One metric as JSON: name, value, provenance, basis, availability (incl. reason when unavailable). Serialization of unit-12 Metric via `as_dict()`.

- **Descent**: reporting.metrics.Metric.as_dict().

### ProvenanceBadge
The UI element showing [mechanical]/[parsed]/[claimed] next to every metric. No data of its own; renders MetricPayload.provenance with the unit-9 badge styling.

- **Descent**: intent FR-13.7; unit-12 provenance labels.

### FilterControls (on the runs list page)
since (date input), until (date input), status (multi-select of success/failed/interrupted/running). Values round-trip to /runs/data query params; invalid input is rejected server-side with 400 (mirrors unit-12 apply_filters).

- **Descent**: unit-12 `apply_filters(since, until, statuses)` + STATUS_VALUES (v1 filters only; pipeline/workspace deferred by unit-12 FD-Q1).

### ChartSlot (resolved by user selection)
Placeholder containers in the detail view (and aggregate view) where charts render. Selection resolved (FD-Q4, 2026-11-09): Apache ECharts 6.1.0 common bundle, vendored and pinned, SVG renderer; chart idioms validated in the spike (verdict strips via thick-line segments, timeline via stacked area bands + stepped line, durations/trend as bars/smoothed lines). Server already serves the structured chart data inside RunDetailPayload.

- **Descent**: FD-Q4 answer; planning-docs/unit-13-charting-selection.md (Phase 5 validated model).

### HistoryMode (report server mode)
`agentic-dev-loop report [--port N] [--runs-root DIR] [--audit-dir DIR]`: serves the runs view without a pipeline file; / and /runs serve RunsPage; /topology and /events are absent. The live run viz keeps the live page AND serves the /runs routes (History link).

- **Descent**: FD-Q1 A; engine/cli.py report command.

## Relationship summary

RunsPage -> GET /runs/data -> RunsListPayload (RunsRecordSummary + MetricPayloads); RunDetailPage -> GET /runs/<id>/data -> RunDetailPayload (threads, attempts, verdicts, MetricPayloads, artifacts); FilterControls -> query params on /runs/data; ChartSlot consumes RunDetailPayload structured fields post-selection; HistoryMode and pipeline mode share the same handler routes.

## Out of scope (no entity)

Pipeline/workspace filter controls (deferred by unit-12 FD-Q1), token/cost metrics, any write path, any new styling framework. Charting is IN scope (ECharts common bundle per FD-Q4 resolution).
